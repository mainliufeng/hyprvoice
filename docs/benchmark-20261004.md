# Hyprvoice 笔记本实际测评 · 2026-10-04

本机最值得接入的平衡候选是 **Fun-ASR-Nano**：CPU 速度接近现有方案，旧回归错误率更低，完整对话集也有改善。**Qwen3-ASR-1.7B** 适合准确率优先的选择，但几秒口述通常需要几秒离线计算，并占用约 6.6 GiB RSS。现有 DeepSeek 后处理没有提升逐字保真成绩，换 ASR 也没有让所有语言的最终文字同时更好。本轮完成实际对比与可复现工具，**没有更换日常输入服务、配置或已安装二进制**。

## 测试范围

实际主机为 Intel i9-12900H、20 个逻辑 CPU、系统可见内存 31.06 GiB、Intel Iris Xe，无独立 GPU。全部识别本地运行；只有明确标注 `+ DeepSeek` 的文字阶段联网，使用现有生产 `Rewrite()` 和原有提示词，不上传录音。

先固定 120 条 ASCEND test 对话（中文/英文/混说各 40 条，2–20 秒），30 条相同原录音的 10 dB 白噪声副本，以及旧的 127 条 FLEURS 回归。四个识别系统各完成同一 277 条。现装系统与 Fun-ASR-Nano 另外完成整个 ASCEND test split 的 1,315 条，并分别运行实际 DeepSeek 后处理。两个 Qwen 的完整 ASCEND split 没有运行，不给全量成绩或榜单排名。

录音、权重、配置与分词文件核验通过。三个候选 CPU 运行时从固定 commit 的源码编译，Qwen 使用 OpenBLAS 0.3.34-1 加速；最初未加速的 0.6B 单条测试耗时 38.49 秒，补齐 OpenBLAS 后同一条为 6.11 秒，该未优化构建没有进入下表。详细采样、前文、评分规则和复现命令见 [测评协议](benchmark-protocol.md)。

X-ASR 使用现装 INT8 ONNX encoder/joiner；Qwen 使用原始 BF16 safetensors（CPU encoder 转为 FP32 运算，decoder 保留 BF16 权重）；Fun 使用 F16 GGUF encoder 和 Q8_0 GGUF decoder。没有把不同量化或运行时的发布者速度当成本机数字。

## 同一组 120 条新对话：识别阶段

错误率越低越好。中文看 CER，英文看 WER，中英混说看 MER。时间是该集合的离线计算时间；当前方案的 `total_ms` 包含模拟快速送入音频时的流式计算与精修，不等于实际松开快捷键后的等待时间。候选模型常驻，初始化不计入单条时间。

| 本地识别系统 | 中文 CER | 英文 WER | 混说 MER | 计算耗时 P50 / P95 | 整个 277 条运行峰值 RSS |
|---|---:|---:|---:|---:|---:|
| 现装 X-ASR 流式＋离线精修 | 8.42% | 24.18% | 9.12% | 0.316 / 0.761 秒 | 约 0.93 GiB¹ |
| Qwen3-ASR-0.6B | 8.42% | **16.03%** | 9.71% | 2.285 / 4.493 秒 | 2.94 GiB |
| Qwen3-ASR-1.7B | **7.35%** | 17.93% | **7.35%** | 3.969 / 6.289 秒 | 6.56 GiB |
| Fun-ASR-Nano（F16 encoder＋Q8 LLM） | 8.60% | 19.02% | 8.68% | 0.470 / 0.888 秒 | 1.54 GiB |

¹ 当前结果由同配置的全量、噪声及旧回归运行组成，0.93 GiB 是旧回归进程的峰值；全量进程峰值为约 0.82 GiB，不是一个单独 277 条进程的测量。候选是单个 277 条常驻进程。RSS 不包含其他日常应用和全部系统缓存。

此集合的加权计算 RTF：当前 0.094、Qwen 0.6B 0.617、Qwen 1.7B 1.030、Fun 0.128。RTF=1 表示计算用时与录音长度相当。候选为 8 线程，现装 X-ASR 按生产配置为 1 线程；这是可部署配置对比，不是相同线程数的算法效率实验。

## 同一组 30 条新加噪对话

| 识别系统 | 中文 CER（11 条） | 英文 WER（12 条） | 混说 MER（7 条） |
|---|---:|---:|---:|
| 当前 X-ASR | 13.86% | 26.36% | 29.90% |
| Qwen 0.6B | 12.65% | 20.00% | 30.93% |
| Qwen 1.7B | 12.05% | 20.00% | 19.59% |
| Fun-ASR-Nano | 15.06% | 25.45% | 14.43% |

样本少，尤其混说只有七条，不能说 Fun 对所有噪音最好。其优势部分来自少漏内容，例如 `ascend-test-01278-white-10db`：当前输出“可以用 mobi 是一些 morn 里面”，Fun 保留了“但是大多数一些奢侈品品牌或者是一些……”这一大段，但仍把参考中的 `mall` 识别成 `MOON`。这是实际输出，不是完美转录。

## 旧 127 条回归

| 识别系统 | CER（7,519 个参考字符） | 静音/白噪声/列车无语音误插入 |
|---|---:|---:|
| 当前 X-ASR | 9.31% | 0 / 3 |
| Qwen 0.6B | 6.20% | 0 / 3 |
| Qwen 1.7B | 3.70% | 0 / 3 |
| Fun-ASR-Nano | 5.13% | 0 / 3 |

这组已被研发查看过，适合确认兼容与退步，不能当新盲测。Qwen 主比较使用 20 秒分段，0.6B 的一条英文拼接长录音出现重复生成，耗时约 94 秒；因此不能只看它在短英文上的优势。

随后单独诊断四条长录音的整段模式（`segment=0`），没有将挑出的较好结果替换主表：0.6B 的两条英文 CER 从 22.38% 降至 7.80%，两条合计计算时间从 102.30 秒降至 13.86 秒；中文 CER 则从 1.23% 升至 1.54%。1.7B 英文 CER 为 3.23% → 2.78%，中文 0.62% → 1.23%。整段模式峰值 RSS 为 0.6B 3.03 GiB、1.7B 6.63 GiB。分段策略能影响质量、重复生成与速度，不能把一个运行时配置的缺陷泛化成模型结论；这四条是已查看数据的诊断。

## 完整 ASCEND test：当前与 Fun

| 识别 / 工作流 | 中文 CER（685 条） | 英文 WER（257 条） | 混说 MER（373 条） | 全集加权 MER |
|---|---:|---:|---:|---:|
| 当前 X-ASR，未加文字处理 | 13.96% | 27.88% | 12.63% | 13.91% |
| Fun-ASR-Nano，未加文字处理 | 9.32% | 24.78% | 12.12% | 11.99% |
| **当前实际文字工作流：X-ASR＋前文＋DeepSeek** | **17.06%** | **32.96%** | **16.06%** | **17.59%** |
| Fun-ASR-Nano＋相同前文＋相同 DeepSeek | 12.92% | 33.36% | 15.22% | 15.96% |

前文取自同一说话人之前的公开正确参考文字，模拟已经输入的正确键盘内容。这是额外上下文条件下的工程工作流测评，不能提交为仅音频输入的 ASCEND 标准榜单成绩。也不代表实际输入框读取、连续听写或上屏完整验收。

短片段对全量结果影响很大：当前 VAD 把 102 条中文片段判为无语音，Fun 能为其中 97 条给出文字。只看至少 2 秒的全部 test 片段，当前/Fun 中文 CER 为 **7.21% / 6.86%**（214 条），英文 WER **21.84% / 18.07%**（100 条），混说 MER **11.31% / 10.92%**（306 条）。因此中文全量的大幅改善不能全部解释为长口述识别模型更强；VAD、短语音与识别模型共同影响系统成绩。

现有精修确实有价值：同一全量中，仅取实际流式终稿时，中文 CER 15.56%、英文 WER 32.88%、混说 MER 13.86%，均高于现有流式＋离线精修。

## 后置大模型的作用与问题

同一 120 条新对话，使用相同生产提示词后：

| 带公开前文的工作流 | 中文 CER | 英文 WER | 混说 MER |
|---|---:|---:|---:|
| 当前 X-ASR＋DeepSeek | 11.11% | 32.34% | 14.12% |
| Qwen 0.6B＋DeepSeek | 13.80% | 26.36% | 13.24% |
| Qwen 1.7B＋DeepSeek | 10.57% | 23.37% | 11.18% |
| Fun-ASR-Nano＋DeepSeek | 13.08% | 27.99% | 15.29% |

Qwen 1.7B 的这个工作流在三项上低于当前工作流，但耗时与内存更高；Fun 没有在这 120 条最终文字上全面胜过当前工作流。因此“ASR 更好”与“最终文字工作流全面更好”是两种结论。

既有 `correct` 提示词会删口头词、纠正语法；公开参考保留原话，成绩必然会受这些合法整理影响，不能把 CER/WER 当成可读性评分。但实际输出也显示语言/措辞保护需要单独处理：例如当前输出 `Uh, some program language like Python.` 被处理成 `嗯，some programming languages like Python.`，英文口述被引入了中文。这个 benchmark 没有为提高分数修改提示词。

全量当前流程调用 DeepSeek 1,182 次，30 次连接在约 5 秒超时；Fun 流程调用 1,302 次，29 次连接超时。对应失败率为 2.54% / 2.23%。均不重试，保留原文并要求手动确认，成绩包含这些保留下来的原文，不能当成全部自动提交成功。批量调用为四个 worker，服务商模型别名为 `deepseek-chat`。

## 选择与边界

推荐后续先把 **Fun-ASR-Nano 接入为可选识别后端**，保留现有快捷键、预览、前文获取和输入保护。它已有本机速度与全量质量证据；集成时仍须重新测整条录音、取消、预览和上屏链路，且不能简单保留会漏掉短语音的旧 VAD 后就照搬独立 Fun 系统的分数。Qwen 1.7B 可作为精度优先选项，当前数据不支持把它称为低延迟默认替换。

前文判断继续作为独立功能保留。自动上下文纠错与用户主动选择的去口头词/整理应分别评价；当前生产提示词的具体调整还没有在新保真测试中验证。本轮没有为了逐字分数关闭用户要求的前文功能。

Qwen/Fun 的语言模型是识别模型内的解码器，可以完全在本地运行；它与“识别完再调用 DeepSeek”不同。普通 ASR benchmark 可以测整个最终转录系统，但不会自动测输入法快捷键、焦点、界面、上屏与语义整理质量。[SpeechColab 的系统接入说明](https://github.com/SpeechColab/Leaderboard)、[Qwen3-ASR 官方说明](https://github.com/QwenLM/Qwen3-ASR)、[Fun-ASR-Nano 的官方 CPU 模型说明](https://huggingface.co/FunAudioLLM/Fun-ASR-Nano-GGUF)支持这些候选路径；它们的发布者评测数字没有混入本机实测表。

FireRedASR2-LLM 也有 Encoder-Adapter-LLM 架构和领先的发布者报告，但本轮没有在这台机器上实测，不据其 GPU 路径或报告推断本机速度。[官方模型与评测](https://github.com/FireRedTeam/FireRedASR2S)。没有微信/豆包输入法客户端同录音输出，不声称胜过它们。
